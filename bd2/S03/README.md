## 1. Errores reales que S1 no manejaba

| # | Error | Qué pasaba en S1 | Ahora |
|---|---|---|---|
| 1 | Otra transacción tiene el producto bloqueado (el backend vendiéndolo) | `FOR UPDATE` sin límite: el procedimiento **esperaba para siempre** | `FOR UPDATE WAIT 10`, igual que `VentaRepository.bloquear()` en Java (10 s); responde ORA-20017 |
| 2 | Nombre del vendedor de más de 60 caracteres | ORA-12899 crudo, con el nombre interno de la tabla y la columna | Excepción con nombre (`PRAGMA EXCEPTION_INIT(-12899)`) → ORA-20018 con un mensaje claro |
| 3 | Cliente inexistente | Se contaba con `COUNT(*)` y se lanzaba ORA-20010, sin registro | `SELECT INTO` con `NO_DATA_FOUND`, en su propio bloque |
| 4 | Un solo `WHEN NO_DATA_FOUND` al final de todo | **Cualquier** `NO_DATA_FOUND`, viniera de donde viniera, se informaba como "el producto no existe" | Cada `SELECT INTO` tiene su bloque y su mensaje |
| 5 | Ningún error quedaba registrado | Si Lucy decía "no me deja vender", no había forma de saber por qué | Todo error se registra en `LOG_ERRORES` **antes** de relanzarse |

## 2. Tabla de registro de errores

```sql
CREATE TABLE log_errores (
    id_log          NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    objeto          VARCHAR2(60)   NOT NULL,      -- procedimiento o función donde ocurrió
    codigo_error    NUMBER         NOT NULL,      -- SQLCODE: 100 (NO_DATA_FOUND), -1, -20xxx…
    mensaje_error   VARCHAR2(500),
    contexto        VARCHAR2(500),                -- parámetros con los que se llamó
    traza           VARCHAR2(1000),               -- DBMS_UTILITY.FORMAT_ERROR_BACKTRACE: en qué línea
    fecha_evento    TIMESTAMP      DEFAULT SYSTIMESTAMP NOT NULL,
    usuario_oracle  VARCHAR2(128)  DEFAULT USER NOT NULL,
    programa        VARCHAR2(64)
);
```

No tiene **ninguna FOREIGN KEY**, porque el error de un cliente inexistente no podría registrarse si
`contexto` apuntara a `CLIENTES`. Respecto de la tabla de la guía, agrega dos columnas:

- **`contexto`**: los parámetros de la llamada, para reproducir el error.
- **`traza`**: la línea exacta del código donde ocurrió.

La escribe un solo procedimiento con **transacción autónoma**:

```sql
CREATE OR REPLACE PROCEDURE sp_registrar_error(p_objeto IN VARCHAR2, p_codigo IN NUMBER,
                                               p_mensaje IN VARCHAR2, p_contexto IN VARCHAR2 DEFAULT NULL) IS
    PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
    INSERT INTO log_errores (objeto, codigo_error, mensaje_error, contexto, traza, programa)
    VALUES (SUBSTR(p_objeto, 1, 60), p_codigo, SUBSTR(p_mensaje, 1, 500), SUBSTR(p_contexto, 1, 500),
            SUBSTR(DBMS_UTILITY.FORMAT_ERROR_BACKTRACE, 1, 1000), SUBSTR(SYS_CONTEXT('USERENV', 'MODULE'), 1, 64));
    COMMIT;   -- confirma SOLO esta fila; no toca la transacción de quien llama
END;
```

Por qué hace falta la transacción autónoma: es el hallazgo principal de la sesión (sección 6).

## 3. Excepciones incorporadas

| Tipo | Excepción | Dónde | Cuándo ocurre de verdad | Código que devuelve |
|---|---|---|---|---|
| **Predefinida** | `NO_DATA_FOUND` | `SELECT id INTO v_cliente FROM clientes …` | Lucy elige un cliente que otra persona acaba de borrar, o un script manda un ID equivocado | ORA-20010 (`SQLCODE` registrado: **100**) |
| **Predefinida** | `NO_DATA_FOUND` | `SELECT … FROM productos … FOR UPDATE WAIT 10` | Producto inexistente | ORA-20015 (registrado: 100) |
| **Personalizada, `PRAGMA EXCEPTION_INIT`** | `e_fila_ocupada` (-54) y `e_fila_ocupada_19c` (-30006) | El mismo `SELECT … FOR UPDATE WAIT 10` | Otra venta o compra del mismo producto está en curso | ORA-20017 |
| **Personalizada, `PRAGMA EXCEPTION_INIT`** | `e_valor_largo` (-12899) | `INSERT INTO ventas` | El nombre del vendedor pasa de 60 caracteres | ORA-20018 |
| **Personalizada, `RAISE_APPLICATION_ERROR`** | Reglas de negocio | Procedimiento local `fallar()` | Descuento sobre el tope (-20012), cantidad ≤ 0 (-20016), stock (-20013), moneda (-20011), más de 700 soles (-20014) | El mismo código |
| Red de seguridad | `WHEN OTHERS` | Final del procedimiento | Cualquier error no previsto | Se registra y se **relanza** con `RAISE` (nunca `THEN NULL`) |

Cuál de las dos formas de excepción personalizada se usa depende de quién genera el error:

- **`PRAGMA EXCEPTION_INIT`** sirve cuando el error **lo genera Oracle** (ORA-00054, ORA-12899) y se le quiere
  dar un nombre para atraparlo solo a él.
- **`RAISE_APPLICATION_ERROR`** sirve cuando el error **no existe en Oracle**. Que un descuento de 25 % supere
  el tope de Lucy solo lo sabe la regla de JD, así que el código lo crea el procedimiento.

El orden en todos los casos es: **primero registrar, después relanzar**. Si se relanza primero, la ejecución
sale del bloque y la línea del registro nunca corre.

## 5. Relación con ADS y LP2

| Objeto BD2 | Decisión ADS | LP2 |
|---|---|---|
| `SP_REGISTRAR_ERROR` + `LOG_ERRORES` | Auditabilidad y diagnóstico (atributo 3, ADS S1) | Complementa los logs de `logback-spring.xml`: Oracle registra lo que pasa adentro de la base, el log de Java la petición completa |
| `FOR UPDATE WAIT 10` y ORA-20017 | Integridad con concurrencia (atributo 1) | El mismo límite que `VentaRepository.bloquear()` (`jakarta.persistence.lock.timeout = 10000`) |
| ORA-200xx con mensaje claro | Usabilidad: Lucy entiende qué pasó | `GlobalExceptionHandler` traduce a 400/404/409 las reglas de Java; las de Oracle se verán al integrar |

## 6. Error o hallazgo

**Hallazgo 1: el registro de errores de la guía se pierde.** El patrón de la guía es
`INSERT INTO log_errores …` seguido de `RAISE_APPLICATION_ERROR`. Se probó tal cual (`S03_02`):

```
A) INSERT directo y luego RAISE              → QUEDARON_SIN_AUTONOMA = 0
B) SP_REGISTRAR_ERROR (autónoma) y luego RAISE → QUEDARON_CON_AUTONOMA = 1
C) Quien llama hace ROLLBACK (como Spring)    → solo queda PRUEBA_ROLLBACK_CON (1 fila)
```

Cuando una excepción sale de un bloque PL/SQL hacia el cliente, Oracle deshace **todo** lo que hizo esa
llamada, porque la sentencia es atómica, y eso incluye el `INSERT` del registro. Y si el cliente es el backend,
Spring hace `ROLLBACK` de la transacción al recibir la excepción. En los dos casos, el registro desaparece
justo cuando más se necesita. **Corrección:** el registro lo hace `SP_REGISTRAR_ERROR` con
`PRAGMA AUTONOMOUS_TRANSACTION`, que confirma solo su propia fila. Se usa únicamente para el registro, nunca
para datos del negocio: una venta en transacción autónoma podría quedar confirmada a medias.

**Hallazgo 2: Oracle 23 no da el error que esperaba.** La primera versión capturaba ORA-30006, que es lo que
documentan las versiones anteriores para un `FOR UPDATE WAIT` vencido. Con dos sesiones reales, Oracle 23
respondió **ORA-00054** (`Failed to acquire a lock … ORA-40097`). La excepción con nombre no lo atrapó. Lo
salvó el `WHEN OTHERS` final, que registró y relanzó, y por eso el error quedó en `LOG_ERRORES` con código
-54 y se pudo diagnosticar. Si ese `WHEN OTHERS` hubiera sido `THEN NULL`, la venta habría "fallado sin
error". **Corrección:** se nombran las dos (-54 y -30006), y la prueba repetida responde ORA-20017 a los 10 s.

## 7. Reflexión

¿Por qué capturar un error y no volver a lanzarlo puede ser peor que no manejarlo?

Un error sin manejar, al menos, se ve: el backend recibe la excepción, deshace la transacción y Lucy ve un
mensaje. Un error capturado y no relanzado (`WHEN OTHERS THEN NULL`) desaparece. El procedimiento termina
"bien", quien llama confirma, y queda una venta a medias o ninguna venta, sin que nadie lo sepa. En SGE-JD eso
significaría una factura enviada a SUNAT sin su venta, o un stock descontado sin venta registrada, y se
descubriría semanas después, al cuadrar el inventario. El hallazgo 2 lo mostró en pequeño: el error que mi
código no esperaba (ORA-00054) se diagnosticó solo porque el `WHEN OTHERS` lo registró y lo relanzó.
Registrar es para entender. Relanzar es para que el sistema no siga como si nada hubiera pasado.
